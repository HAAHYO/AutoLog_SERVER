# AutoLog 백엔드 오케스트레이터

1인 프로젝트용 경량 하네스입니다. 리더(메인 세션)가 계약을 쓰고, 구현은 두 엔지니어가 병렬로 하며, QA가 레이어 경계를 교차 검증합니다.

## 왜 이렇게 나눴나

- 이 서비스에서 가장 비싼 결함은 **두 파일 사이**에서 생깁니다. 예를 들면 DTO는 non-null인데 엔티티 상태상 null일 수 있는 경우, 서비스가 던지는 예외가 계약의 실패 표와 다른 경우, 원장 분개의 차변과 대변 합계가 맞지 않는 경우입니다.
- 그래서 구현한 사람이 아닌 **별도의 QA 에이전트가 양쪽 파일을 동시에 읽고** 확인합니다.
- API 계약과 Git 작업은 리더가 직접 맡습니다. 1인 프로젝트에서 이 둘을 별도 에이전트로 두면 비용만 늘고 얻는 것이 거의 없습니다.

## 팀 구성

| 멤버 | subagent_type | 담당 | 출력 |
|------|--------------|------|------|
| 리더 (메인 세션) | — | 요구사항, API 계약, 통합, 빌드, 커밋/PR | `_workspace/01_contract.md`, 최종 요약 |
| domain-engineer | `domain-engineer` | 엔티티, 리포지토리, 서비스, ErrorCode | `_workspace/02_domain_notes.md` |
| web-engineer | `web-engineer` | 컨트롤러, 요청/응답 DTO | `_workspace/03_web_notes.md` |
| qa-inspector | `qa-inspector` | 교차 검증 | `_workspace/04_qa_report.md` |

에이전트는 `Agent` 도구로 띄웁니다. 각 에이전트는 새 컨텍스트에서 시작하므로, 프롬프트에 **계약 파일 경로, 대상 파일 경로, 읽어야 할 스킬**을 반드시 적어 줍니다.

## 워크플로

### Phase 0: 실행 모드 판단

1. 저장소 루트에 `_workspace/`가 있는지 확인합니다.
2. 결과에 따라 실행 모드를 고릅니다.
   - **없으면** → 최초 실행입니다. Phase 1로 갑니다.
   - **있고, 부분 수정 요청이면**("QA 다시", "QA 지적 사항 수정") → 부분 재실행입니다. 필요한 에이전트만 띄우고, 각자의 이전 노트 경로를 넘겨 "새로 만들지 말고 수정하라"고 지시합니다.
   - **있고, 무관한 새 기능이면** → `_workspace/`를 `_workspace_<YYYYMMDD_HHMMSS>/`로 옮기고 Phase 1로 갑니다.
3. 부분 재실행에도 **항상 qa-inspector를 포함**합니다. 코드가 바뀌면 이전 QA 결과의 일부가 무효가 되기 때문입니다.

### Phase 1: 준비 (리더)

1. `docs/PRODUCT.md`와 `docs/IMPLEMENTATION-STATUS.md`를 읽습니다.
   - 요청이 미결정 제품 질문이나 아직 없는 기능에 의존하는지 확인합니다.
   - 의존한다면 **팀을 띄우기 전에** 사용자에게 알립니다.
2. 브랜치를 확인합니다. 요청이 `docs/IMPLEMENTATION-STATUS.md` "브랜치 계획"의 어느 묶음에 속하는지 보고, 그 묶음의 브랜치가 이미 있으면 **그 브랜치에서 이어서** 작업합니다. 없으면 최신 `develop`에서 묶음 이름으로 만들고 사용자에게 알립니다. 작은 작업 하나만을 위한 브랜치는 만들지 않습니다.
3. `_workspace/00_input/request.md`에 요청과 제약을 적습니다.
4. `_workspace/00_input/baseline.md`에 `git rev-parse HEAD`와 `git status --short` 결과를 기록합니다.
5. 관련 기존 소스를 읽어 둡니다. 에이전트 프롬프트에 실제 파일 경로를 적기 위해서입니다.

### Phase 2: 계약 (리더)

1. `api-contract` 스킬 형식으로 `_workspace/01_contract.md`를 작성합니다.
2. 금액, 원장, 주문 체결이 관련된 작업이라면 `money-ledger` 스킬을 읽고, 계약의 "불변식" 항목을 채웁니다. Kafka, Redis, 락이 관련된 작업이라면 `kafka-redis-pipeline`도 읽고, 계약 Notes에 토픽, 키, 락 단위, 멱등 처리 방식을 적습니다.
3. 작업에 아직 없는 의존성(QueryDSL, Redis, Kafka, Testcontainers)이 필요하다면 **팀을 띄우기 전에** 사용자에게 추가해도 되는지 확인합니다.
4. 실패 표의 동작이 제품 결정에 해당한다면(예: 잔액 부족 주문을 거절할지, 대기시킬지) 두 가지 안을 모두 적고 **사용자에게 물어봅니다.** 혼자 고르지 않습니다.

### Phase 3: 구현 (병렬)

`domain-engineer`와 `web-engineer`를 **한 메시지 안에서 동시에** 띄웁니다. 계약에 서비스 시그니처가 확정되어 있으므로 서로 기다릴 필요가 없습니다.

프롬프트 예시:

```
domain-engineer:
  "<기능>의 엔티티/리포지토리/서비스/ErrorCode를 구현해.
   먼저 .claude/skills/java-spring-conventions, jpa-domain, money-ledger 스킬을 읽어.
   (Kafka/Redis/락이 포함되면 kafka-redis-pipeline도)
   계약: _workspace/01_contract.md. 기존 코드: <경로들>.
   서비스 시그니처는 계약과 정확히 일치시켜.
   _workspace/02_domain_notes.md에 '## 스키마 영향' 섹션을 반드시 포함해."

web-engineer:
  "<기능>의 컨트롤러와 요청/응답 DTO를 구현해.
   먼저 java-spring-conventions, api-contract 스킬을 읽어.
   계약: _workspace/01_contract.md.
   서비스는 계약의 시그니처대로 존재한다고 가정해.
   _workspace/03_web_notes.md를 남겨."
```

두 에이전트가 같은 파일을 수정하지 않도록 소유권을 나눕니다.

- `dto/` 아래 파일은 web-engineer가 맡습니다.
- 응답 DTO의 `from()`은 web-engineer가 작성하되, 엔티티 게터 이름은 계약을 기준으로 맞춥니다.

### Phase 4: 검증

1. 두 엔지니어가 끝나면 리더가 직접 `./gradlew compileJava`를 실행합니다. 에이전트의 보고만 믿지 않습니다.
2. 컴파일이 실패하면 오류를 원인 쪽 에이전트에게 넘겨 한 번 더 시킵니다. 두 번째에도 실패하면 리더가 직접 고치고, 그 사실을 기록합니다.
3. `qa-inspector`를 띄워 `qa-verify` 스킬의 전체 체크를 실행하게 합니다.
4. BLOCKER가 나오면 해당 에이전트에게 수정을 맡기고, QA는 **수정된 경계만** 다시 확인합니다. 이 왕복은 최대 2회입니다.
5. 리더가 `./gradlew build`를 실행합니다.

### Phase 5: 마무리

1. `_workspace/` 노트를 모두 읽고 최종 요약을 작성합니다(아래 형식).
2. 커밋은 **사용자가 요청한 경우에만** `git-commit-convention`에 따라 리더가 합니다.
3. 푸시와 PR 생성은 사용자에게 확인한 뒤 `github-pr-author`에 따라 진행합니다.
4. `_workspace/`는 지우지 않습니다. 다음 부분 재실행의 입력으로 쓰입니다(`.gitignore`에 포함되어 있음).

## 에러 처리

| 상황 | 대응 |
|------|------|
| 에이전트가 실패하거나 결과가 비어 있음 | 한 번 재시도합니다. 다시 실패하면 리더가 해당 부분을 직접 하고 요약에 적습니다. |
| QA와 엔지니어의 의견이 다름 | 리더가 인용된 양쪽 파일을 직접 읽고 결정합니다. 왕복은 2회까지입니다. |
| 계약과 엔티티가 모순됨 | 엔티티(실제 런타임)를 기준으로 하고 계약을 고칩니다. 수정한 사실을 기록합니다. |
| 구현이 `docs/PRODUCT.md`와 다름 | 조용히 맞추지 않고 보고합니다. 문서는 사용자가 동의할 때만 고칩니다. |
| `ddl-auto: update`로 안전하지 않은 스키마 변경 | 해당 작업을 멈추고, 필요한 수동 SQL을 사용자에게 먼저 보여줍니다. |
| 원장 불변식이나 체결 동시성 관련 BLOCKER가 남음 | 작업을 **완료로 보고하지 않습니다.** 요약 맨 위에 적습니다. |
| H2에서만 확인됨 (락, DECIMAL 등) | "확인하지 못함"에 "MySQL 미검증"으로 적습니다. |
| Kafka/Redis를 띄우지 않고 정적으로만 확인함 | "확인하지 못함"에 "Kafka/Redis 통합 미검증"으로 적습니다. Docker Compose가 생긴 뒤에는 띄워서 확인할 수 있는지 먼저 시도합니다. |

## 최종 요약 형식 (한국어)

```markdown
## <기능> — 완료 | 막힘

**변경:** 파일 <n>개 (<레이어들>)
**빌드:** compileJava PASS | build PASS/FAIL/미실행(<이유>)
**QA:** BLOCKER <n> / MAJOR <n> / MINOR <n> — 미해결 <n>

### 엔드포인트
| Method | Path | 설명 | 상태 |

### 미해결 / 결정 필요
- ...

### 스키마 영향
- <필요한 수동 SQL, 또는 "없음 — 추가만 있음">

### 확인하지 못함
- <실행하지 못한 검증과 이유>
```

마지막 두 섹션(스키마 영향, 확인하지 못함)은 항상 적습니다.

## 부분 재실행 예시

| 사용자 요청 | 띄울 에이전트 | workspace |
|-------------|---------------|-----------|
| "QA 다시 돌려줘" | qa-inspector | 재사용, 리포트에 날짜 섹션 추가 |
| "QA에서 나온 거 고쳐줘" | 지적된 엔지니어 + qa-inspector | 재사용 |
| "계약이 X가 틀렸어" | (리더가 계약 수정) + 영향받는 엔지니어 + qa-inspector | 재사용 |
| "같은 도메인에 엔드포인트 추가" | 전체 | 재사용, 내용 추가 |
| "관련 없는 새 기능" | 전체 | 기존 것을 아카이브하고 새로 시작 |
| "커밋하고 PR 올려줘" | 없음 (리더가 직접) | 재사용 |

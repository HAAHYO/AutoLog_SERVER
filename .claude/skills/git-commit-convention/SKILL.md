# 브랜치·커밋 규칙

## 브랜치 (main + develop)

```
main     ← develop (릴리스 PR, 마일스톤 단위)
develop  ← feat/ledger-core      (원장 핵심 묶음)
         ← feat/rate-streaming   (시세 수집·스트리밍 묶음)
         ← fix/ledger-rounding
```

| 브랜치 | 역할 | 직접 커밋 |
|--------|------|-----------|
| `main` | 릴리스된 안정 버전. 나중에 배포(CD)를 붙일 대상 | **금지**. `develop`에서 오는 릴리스 PR로만 병합 |
| `develop` | 통합 브랜치. 기능 PR의 **base**이며 GitHub 기본 브랜치 | **금지**. 기능 PR 병합, 또는 `main` → `develop` 동기화로만 반영 |
| `<type>/<kebab-주제>` | 작업 브랜치. **`develop`에서 분기** | 자유 |

- 작업 브랜치 이름은 `<type>/<kebab-주제>`입니다. type은 아래 커밋 타입 중 하나입니다.
- **브랜치는 큰 기능 묶음 단위로** 만듭니다. 기준은 MVP 단계나 도메인 묶음입니다(`docs/IMPLEMENTATION-STATUS.md`의 "브랜치 계획").
  - enum 하나 추가, 공통 엔티티 필드 변경 같은 **작은 선행 작업마다 브랜치를 따로 만들지 않습니다.** 그 작업이 필요한 큰 기능 브랜치 안에 커밋으로 넣습니다.
  - 반대로 서로 무관한 큰 기능 두 개를 한 브랜치에 섞지도 않습니다.
  - 커밋은 브랜치보다 작은 **의미 있는 작업 단위**로 나눕니다(아래 "커밋 단위" 참고). 파일마다 쪼개지 않습니다.
- 큰 기능이 끝나면 PR로 `develop`에 병합합니다(`github-pr-author` 참고).
- `fix/*`는 이미 병합된 기능의 버그를 고칠 때만 씁니다. 지금 작업 중인 큰 브랜치에서 발견한 버그는 그 브랜치에서 고칩니다.
- `develop`과 `main`에는 직접 커밋하거나 푸시하지 않습니다. 문서만 바뀌는 수정도 브랜치를 거쳐 PR로 올립니다. 작은 문서 수정은 진행 중인 큰 브랜치에 커밋으로 함께 넣습니다.
- 현재 브랜치가 `develop`이나 `main`인데 커밋을 해야 한다면(코드든 문서든), **최신 `develop`에서** 브랜치를 만들고 사용자에게 알립니다.

  ```bash
  git switch develop && git pull
  git switch -c feat/<주제>
  ```

- hotfix 브랜치(`main`에서 분기)는 운영 배포가 생기기 전까지 쓰지 않습니다. 버그도 `fix/*` → `develop`으로 고칩니다.

## 메시지 형식

```
<type>: <한국어 요약>

(선택) 본문 — 코드만으로는 "왜"가 드러나지 않을 때만 1~3줄
```

- scope 괄호(`feat(order):`)는 쓰지 않습니다.
- 끝에 마침표를 찍지 않습니다.
- 50자 안팎으로 씁니다.
- `Co-Authored-By:` 같은 트레일러는 본문 아래에 붙여도 됩니다.

| Type | 의미 | 예 |
|------|------|-----|
| `feat` | 새로운 기능 | `feat: 지정가 주문 엔티티 추가` |
| `fix` | 버그 수정 | `fix: 환전 금액 반올림 방향 수정` |
| `refactor` | 동작 변화 없는 코드 개선 | `refactor: 분개 생성 로직을 팩토리로 분리` |
| `test` | 테스트 추가·수정 | `test: 분개 차대 균형 검증 테스트 추가` |
| `docs` | 문서 수정 | `docs: 도메인 모델 문서 갱신` |
| `chore` | 빌드, 의존성, CI, 설정, 기타 | `chore: GitHub Actions CI 추가` |
| `init` | 프로젝트 초기화 | `init: Spring Boot 프로젝트 생성` |

요약은 기존 히스토리와 같은 명사형 어미(`추가`, `수정`, `삭제`, `변경`, `분리`)로 끝냅니다. 문장형으로 쓰지 않습니다.

| 나쁜 예 | 좋은 예 | 이유 |
|---------|---------|------|
| `feat: 기능 추가` | `feat: 환율 조회 API 추가` | 무엇인지 드러남 |
| `fix: 버그 수정` | `fix: 지정가 비교 방향 반전 수정` | 어떤 동작인지 드러남 |
| `chore: 수정` | `chore: gitignore에 _workspace 추가` | 파일과 변경이 드러남 |
| `feat: 주문 API, 환율 스트림, 원장 수정` | 커밋을 주제별로 분리 | 서로 무관한 작업이 섞임 |

## 커밋 단위 — 가장 중요한 부분

**의미 있는 작업 단위 하나당 커밋 하나**입니다. 파일마다, 계층마다 쪼개지 않습니다. 기준은 "`git log` 한 줄만 읽고 무엇을 했는지 알 수 있는가"입니다.

> 2026-11-25에 기준을 바꿨습니다. 처음에는 파일이나 관심사마다 커밋을 나눴는데, 커밋이 160개를 넘으면서 오히려 기록을 읽기 어려워졌습니다.

| 변경 | 커밋 |
|------|------|
| `FxOrder` 엔티티 + 리포지토리 + 그 테스트 | **1개** (`feat: 지정가 주문 엔티티와 리포지토리 추가`) |
| 서비스 메서드 + ErrorCode 추가 + 서비스 테스트 | **1개** |
| 컨트롤러 + 요청·응답 DTO + 컨트롤러 테스트 | **1개** |
| 결정 하나를 문서 여러 개에 반영 | **1개** (`docs: 금액 직렬화 결정 반영`) |
| 셀프 리뷰 반영 | 성격별로 **1~3개** (예: 정합성 수정 / 리팩터링 / 문서) |
| 버그 수정과 무관한 파일 포맷 정리 | 2개 (서로 무관하므로) |

- **목표: PR 하나에 커밋 5~15개.** 이보다 훨씬 많다면 너무 잘게 나눈 것이고, 1~2개라면 PR 전체를 뭉친 것입니다.
- **테스트는 그 코드와 같은 커밋**에 넣습니다. 코드를 넣은 커밋과 테스트를 넣은 커밋을 따로 두지 않습니다.
- **서로 무관한 변경은 섞지 않습니다.** 크기와 관계없이 주제가 다르면 커밋을 나눕니다.
- 요약에 "·"나 "와/과"가 들어가는 것은 괜찮습니다. 한 작업 단위를 설명하는 데 필요하다면 써도 됩니다.

### 순서 — 각 커밋이 단독으로 컴파일되도록

1. entity / enum
2. repository
3. `ErrorCode` 상수
4. service
5. DTO
6. controller
7. test, docs, chore

컴파일되지 않는 중간 커밋이 있으면 그 지점으로 체크아웃할 수 없고, `bisect`도 쓸 수 없습니다.

## 절차

1. **실제로 무엇이 바뀌었는지 먼저 봅니다.**
   ```bash
   git status --short
   git diff
   ```
   이번 세션에서 하지 않은 변경이 섞여 있다면 따로 커밋하거나 사용자에게 물어봅니다. 몰래 섞어 넣지 않습니다.
2. **경로를 지정해 한 단위씩 스테이징합니다.** `git add <path>`를 쓰고, `git add -A`나 `git add .`는 쓰지 않습니다.
3. **스테이징된 내용이 메시지와 맞는지 확인합니다.**
   ```bash
   git diff --staged --stat
   ```
4. **커밋합니다.** 한국어가 깨지지 않도록 heredoc을 씁니다.
   - Bash:
     ```bash
     git commit -m "$(cat <<'EOF'
     feat: 지정가 주문 엔티티 추가
     EOF
     )"
     ```
   - PowerShell:
     ```powershell
     git commit -m @'
     feat: 지정가 주문 엔티티 추가
     '@
     ```
5. 단위마다 반복합니다. 끝나면 `git log --oneline develop..HEAD`로 전체 목록을 확인합니다.

## 규칙

- 커밋은 **사용자가 요청했을 때만** 합니다. "이거 고쳐줘"는 커밋 요청이 아닙니다.
- `git add -A`와 `git add .`는 금지입니다.
- 푸시된 커밋에 amend하지 않습니다. force-push하지 않습니다. 대신 새 커밋을 만듭니다.
- `--no-verify`나 서명 우회를 쓰지 않습니다.
- **비밀값을 커밋하지 않습니다.** `application*.yml`은 환경변수 플레이스홀더(`${DB_PASSWORD:}`)를 쓰는 상태를 유지합니다. 새 설정 파일은 스테이징 전에 내용을 확인합니다. `.env`와 `application-secret.yml`은 gitignore되어 있습니다.
- `_workspace/`는 커밋하지 않습니다(gitignore되어 있음).

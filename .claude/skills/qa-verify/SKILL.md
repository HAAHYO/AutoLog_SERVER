# 교차 검증

이 서버에서 운영까지 가는 결함은 대부분 클래스 **안**이 아니라 **두 클래스 사이**에 있습니다. 각각은 맞는데 서로 맞지 않는 경우입니다.

## 빌드가 증명하는 것과 못하는 것

```bash
./gradlew compileJava          # 레이어 간 타입 오류
./gradlew test                 # H2로 컨텍스트 부팅 → 빈 와이어링, 파생 쿼리명, 매핑 검증
git diff --stat main...HEAD    # 변경 범위
```

- `compileJava`는 파생 쿼리명 오타(`findAllByAcountId`)를 잡지 못합니다. 이는 **컨텍스트 부팅 시점**에 실패하므로 `test`까지 돌려야 합니다.
- `test`가 통과해도 H2 기준입니다. 락, DECIMAL, 유니크 제약의 동시성, 시간대 처리는 MySQL에서 미검증입니다.
- 지금 있는 테스트는 `contextLoads()` 하나뿐입니다. 엔드포인트를 실제로 호출하는 테스트가 없다면 "API 동작 검증"은 통과가 아닙니다.

## 체크 목록

각 체크는 **양쪽 파일을 동시에 읽어야** 합니다. 한쪽만 읽고 다른 쪽이 "아마 이렇겠지"라고 추론하면 버그가 살아남습니다.

### 1. Controller ↔ Service

- 컨트롤러가 넘기는 인자와 서비스가 받는 인자가 일치하는지, 서비스의 반환 DTO와 `ResponseEntity<T>`의 T가 일치하는지, 그리고 그것이 계약과 일치하는지 확인합니다.
- 컨트롤러에 비즈니스 로직(`if` 분기), 리포지토리 접근, 엔티티 처리가 없는지 확인합니다.
- 상태 코드(201, 200, 204)가 계약과 일치하는지 확인합니다.

### 2. 요청 DTO ↔ @Valid ↔ 계약

- 요청 record에 제약 애노테이션이 있어도 컨트롤러에 **`@Valid`가 없으면 검증이 실행되지 않습니다.** 반드시 확인합니다.
- 계약에 적힌 단일 필드 제약이 모두 애노테이션으로 들어갔는지 확인합니다.
- 필드 간 제약이나 DB가 필요한 제약은 서비스 가드에 있는지 확인합니다.
- 중첩 객체나 리스트 원소를 검증하려면 해당 필드에도 `@Valid`가 붙어 있어야 합니다.

### 3. 응답 DTO ↔ 엔티티 상태

- `from()`이 record의 모든 컴포넌트를 채우는지 확인합니다.
- 각 필드에 대해 "어떤 상태에서 null일 수 있는가?"를 엔티티 상태 머신과 대조합니다. 계약에서 non-null이라고 했는데 실제로 null이 나갈 수 있다면 결함입니다.
- 엔티티가 응답에 그대로 노출되지 않는지 확인합니다(`ResponseEntity<ExchangeOrder>` 같은 형태 금지).

### 4. 던지는 예외 ↔ 계약 실패 표

- 코드 경로의 모든 `throw`와 계약의 실패 표를 1:1로 대조합니다.
  - throw는 있는데 표에 없으면 문서에 없는 동작입니다.
  - 표에는 있는데 throw가 없으면 지키지 않는 약속입니다.
- 일반 예외(`RuntimeException`, `IllegalArgumentException`, `IllegalStateException`, `NoSuchElementException`이나 `Optional.get()`, `orElseThrow()`의 인자 없는 형태)는 catch-all에 걸려 **500**이 됩니다. 의도된 실패라면 결함입니다.
- `ErrorCode`의 HTTP 상태가 계약의 상태와 같은지 확인합니다.
- 외부 API 호출에서 나는 예외(타임아웃 등)가 어디서 잡히는지 확인합니다.

### 5. 쓰기 메서드 ↔ @Transactional

- 클래스가 `readOnly = true`인 서비스에서, 엔티티를 변경하거나 `save`를 호출하는 **모든 메서드**에 `@Transactional`이 붙어 있는지 확인합니다. 빠지면 변경이 조용히 사라집니다.
- `@Transactional`의 import가 `org.springframework...`인지 확인합니다.
- 같은 클래스 안에서 `@Transactional` 메서드를 호출(self-invocation)하는 곳이 있다면 트랜잭션이 적용되지 않습니다.
- 트랜잭션 안에서 외부 HTTP 호출을 하고 있지 않은지 확인합니다.

### 6. 리포지토리 쿼리명 ↔ 엔티티 필드

- 파생 메서드명을 프로퍼티 경로로 분해합니다. 예: `findAllByAccountIdAndStatusOrderByCreatedAtDesc` → `account.id`, `status`, `createdAt`
- 분해한 각 경로가 엔티티에 존재하고 타입이 맞는지 확인합니다.
- 컬렉션 쿼리에 정렬이 있는지 확인합니다.
- `@Query`가 엔티티·필드명을 쓰는지, `@Param`이 플레이스홀더와 일치하는지 확인합니다.
- `@Modifying` 쿼리의 반환값(영향 행 수)을 호출부에서 확인하는지 봅니다.

### 7. LAZY 연관 ↔ DTO 접근

- 목록을 반환하는 쿼리와 `from()`이 읽는 필드를 대조합니다. `from()`이 LAZY 연관을 읽는데 fetch join이 없으면 **N+1**입니다.
- DTO 변환이 서비스 트랜잭션 **밖**에서 일어나면 `open-in-view: false` 때문에 **LazyInitializationException**이 납니다. 예를 들어 컨트롤러에서 엔티티를 받아 변환하는 경우입니다.

### 8. 금액·원장·체결 불변식 (`money-ledger` 스킬)

관련 코드가 바뀐 경우에만 확인합니다. 해당될 때는 **가장 우선** 확인합니다.

- `double`이나 `float` 금액, `new BigDecimal(double)`, `BigDecimal.equals` 비교, scale이 없는 `divide`가 있는지 봅니다.
- 금액·환율 컬럼에 `precision`과 `scale`이 있는지 확인합니다.
- 분개를 만드는 모든 경로가 통화별 차대 균형 검증을 거치는지 확인합니다.
- 원장 엔티티에 변경 메서드가 있거나, 리포지토리 delete를 호출하는 코드가 있는지 봅니다.
- 멱등키에 **DB 유니크 제약**이 있는지 확인합니다. 코드에서만 확인하고 있다면 결함입니다.
- 잔액 검사와 차감이 같은 락 범위 안에 있는지 확인합니다.
- 주문 체결이 정확히 한 번만 일어나도록 보장하는 장치(조건부 UPDATE, `@Version`, 비관적 락)가 있는지 확인합니다.
- 주문 상태 전이, 분개, 잔액 갱신이 한 트랜잭션에 묶여 있는지 확인합니다.
- 지정가 비교 방향(이상/이하)이 매수·매도 방향과 맞는지, 경계값(같을 때) 처리가 계약과 같은지 확인합니다.
- 체결 시 사용한 환율 값, 시각, 출처를 저장하는지 확인합니다.

## 리포트 형식

`_workspace/04_qa_report.md`에 씁니다. 하네스 없이 셀프 점검할 때는 같은 형식으로 사용자에게 응답합니다.

```markdown
# QA 리포트 — <기능>

## 확인함
| # | 체크 | 결과 | 근거 |
|---|------|------|------|
| 1 | Controller ↔ Service | PASS | ExchangeOrderController.java:31 → ExchangeOrderService.java:48, 둘 다 OrderResponse |

## 발견 사항
### [BLOCKER] <한 줄 결함>
- **위치:** `path/A.java:LINE` ↔ `path/B.java:LINE`
- **실패 시나리오:** 구체적 입력 → 잘못된 결과
- **수정안:** 구체적 변경, 담당 에이전트

## 확인하지 못함
- <체크> — <이유: H2라 MySQL 락 미검증, 엔드포인트 호출 안 함 등>
```

**심각도**

| 등급 | 의미 | 예 |
|------|------|-----|
| BLOCKER | 런타임에 동작이 틀림 | 잔액·원장 오류, 중복 체결, 의도된 실패가 500, `@Transactional` 누락, `@Valid` 누락 |
| MAJOR | 대체로 맞지만 부하나 경계 조건에서 틀림 | N+1, 정렬 누락, null 처리 누락 |
| MINOR | 스타일, 네이밍, 죽은 코드 | |

**"확인하지 못함" 섹션은 필수입니다.** 환경 때문에 실행하지 못한 것이 있다면 절대 비워 두지 않습니다. 언급하지 않은 체크는 통과한 것으로 읽힙니다.

## 보고 원칙

- 경계에 걸친 발견은 **양쪽**의 `file:line`을 인용합니다. 한쪽만 인용했다면 교차 확인을 하지 않은 것입니다.
- 구체적인 실패 시나리오를 씁니다.
  - 좋은 예: "PENDING 주문을 두 스레드가 동시에 체결하면 분개가 2개 생겨 잔액이 두 번 차감된다"
  - 나쁜 예: "동시성 문제 가능성"
- 실행하지 않은 체크를 PASS로 적지 않습니다.
